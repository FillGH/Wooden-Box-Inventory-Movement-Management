# Process Discovery — Wooden Box Material Flow

> **Source:** บทสนทนากับ Process Owner, ตุลาคม 2026 · **Status:** สรุปข้อเท็จจริงจากการเล่า ไม่ใช่การตรวจสอบหน้างานอย่างเป็นทางการ
>
> **Public-safe version:** ใช้ Supplier A/B และข้อมูลตัวอย่างสมมติ ไม่คัดลอกใบส่งของ รูปเอกสาร หมายเลขธุรกรรม ชื่อลูกค้า หรือพนักงานจริง

## 1. Current Process (As-Is)

1. PPIC ทราบแผนผลิตและปริมาณลังที่ต้องใช้
2. Purchasing ประสาน Supplier A และ Supplier B เรื่องจำนวน กำลังผลิต วันส่ง และราคา
3. Supplier นำชิ้นส่วนลังไม้พร้อม Invoice/Delivery Document มาส่งที่ Cutting & Packing
4. ทีมรับของตรวจนับของจริงเทียบเอกสาร แล้วเขียนบนกระดาษว่าตรง/ขาด/เกิน/ชำรุด/ค้างส่ง
5. นำของไปวางในพื้นที่จัดเก็บ ซึ่งอาจเป็นพื้นที่ชั่วคราวและกระจายหลายจุด
6. คนอีกกลุ่มนำข้อมูลไปบอกผู้ใช้หรือผู้ที่ต้องขับ Forklift ไปนำลังออก
7. เมื่อมีการย้ายหรือเบิกใช้ ไม่มีระบบสต๊อกเฉพาะงานนี้ที่อัปเดตต่อเนื่อง จึงอาจต้องไปนับใหม่

**นี่เป็นบริบทของปัญหา ไม่ใช่ขอบเขตระบบ:** PPIC และ Purchasing จะยังทำงานในกระบวนการเดิมต่อไป; Web App V1 จะไม่รับเข้าแผนหรือ PO จากสองฝ่าย

## 2. Physical Facts

- ลังหนึ่งหน่วยประกอบด้วย **Top 1 + Bottom 1 + Side 2** (ตามการอธิบายกระบวนการปัจจุบัน)
- มี Supplier หลักสองเจ้าซึ่งรูปแบบเอกสารและการส่งของต่างกัน
- เจ้าหนึ่งมักส่งชุดครบ อีกเจ้าอาจทยอยส่ง Top/Bottom/Side ไม่เท่ากัน
- ชิ้นส่วนถูกใช้กับสเปกกระจกต่างกัน เช่น ความหนา ขนาด จำนวนแผ่นต่อลัง เกรด/ลูกค้า และวัสดุคั่นกระจก
- พื้นที่เก็บมีข้อจำกัด ไม่ถาวร และมีหลายจุด; ของใหม่อาจขวางของเก่า จนต้องย้ายซ้ำ
- คนรับ คนสื่อสารข้อมูล และคนหยิบ/ขนย้าย ไม่จำเป็นต้องเป็นคนเดียวกัน
- มีของเสีย/เสียหายซึ่งทำให้จำนวนที่มีอยู่ไม่เท่ากับจำนวนที่ใช้ได้จริง

## 3. Representative Scenarios

### Scenario A — Partial Delivery (ข้อมูลสมมติเพื่ออธิบายกติกา)

สั่ง 50 ลัง: ควรมี Top 50, Bottom 50, Side 100. รับ Top 50, Bottom 40, Side 100 → ในเชิงจำนวนชิ้นส่วนสามารถประกอบได้สูงสุด **40 ชุด** โดยยังไม่ประเมินสภาพหรือความสามารถเข้าถึงพื้นที่จริง

ข้อสรุป: ห้ามบันทึกแค่ 'รับ 50 ลัง' แล้วถือว่าของครบ

### Scenario B — Changed Production Date (เหตุการณ์จริงแบบไม่ระบุข้อมูลภายใน)

แผนผลิตรายการหนึ่งถูกเลื่อนมาเร็วขึ้น แต่กำหนดส่ง Packaging Material ยังอยู่ตามแผนเดิม เมื่อหน้างานต้องใช้จึงต้องโทรประสานหลายคนและค้นหลายพื้นที่ ก่อนทราบว่ายังไม่ได้รับวัสดุที่ต้องการ

**ข้อสรุป:** ปัญหานี้บอกถึงช่องว่างการสื่อสารระหว่าง planning/supply/physical stock แต่การแก้กระบวนการ PPIC/Purchasing **ไม่ใช่ scope V1**. V1 ช่วยให้ตอบได้เฉพาะของที่รับเข้าจริงและสต๊อกที่ยังมีอยู่เท่านั้น

### Scenario C — Location & Movement

เมื่อมีการวางลังใหม่ขวางลังเดิม อาจต้องย้ายไปอีกพื้นที่ เมื่อไม่มี movement history ผู้ใช้คนถัดไปไม่รู้ว่าของย้ายไปไหน

**ข้อสรุป:** ต้องรู้ตำแหน่งปัจจุบันและบันทึกเหตุการณ์ Move โดยไม่เปลี่ยนยอดรวม

## 4. Problem Themes

| Dimension | Observed pain | V1 response |
|---|---|---|
| Information handoff | กระดาษ → คนกลาง → คนใช้ | บันทึกครั้งเดียว แล้วค้นจากระบบ |
| Partial receiving | จำนวน Top/Bottom/Side ไม่เท่ากัน | บันทึก component แยก |
| Location visibility | พื้นที่ชั่วคราวหลายจุด | Location พร้อมการย้าย |
| Inventory accuracy | ไม่รู้ยอดปัจจุบัน ต้องนับใหม่ | Movement-based balance และตรวจนับยืนยัน |
| Damage | ของมีแต่ใช้ไม่ได้ | สถานะ/จำนวนชำรุด |
| Plan-vs-delivery | แผนเปลี่ยนแต่กำหนดส่งไม่เปลี่ยน | **รับทราบปัญหา แต่ไม่ทำ auto readiness ใน V1** |

## 5. User / Environment

- **Receiver:** บันทึกข้อมูลรับจริงและข้อยกเว้น
- **Supplier:** ส่งชิ้นส่วนและเอกสาร; การให้ใช้แอปโดยตรงยังไม่ยืนยัน
- **Supervisor:** ค้นข้อมูล ประเมินและสื่อสารสต๊อก
- **Forklift Operator:** ค้นหา ย้าย และเบิกใช้วัสดุ
- ใช้มือถือส่วนตัวได้ แต่ไม่มี PC/tablet ที่หน้างานเป็นอุปกรณ์หลัก
- Internet อาจขาดช่วง; ควรออกแบบไม่ให้เกิดข้อมูลลวงว่า 'บันทึกสำเร็จแล้ว' ในขณะที่ยังไม่เข้า server
- ไม่ใช้งานมือถือขณะขับหรือเคลื่อนย้ายวัสดุ

## 6. Key Engineering Insight

**เป้าหมายไม่ใช่ทำให้คนกรอกหลายรายการได้เร็วขึ้นอย่างเดียว แต่ต้องลดการกรอกซ้ำ และให้ stock เป็นผลลัพธ์จากธุรกรรมที่เกิดจริง**

ปัญหาพื้นที่จัดเก็บจำกัดและลังซ้อน/บังกันเป็นข้อจำกัดทางกายภาพที่โปรแกรมไม่สามารถแก้ได้ลำพัง

## 7. Evidence Limits

เอกสารนี้ไม่ใช่ผล Gemba walk, ไม่มีการวัดเวลาจริงหรือ stock accuracy baseline และไม่มีการยืนยันรายชื่อ Supplier/Location/SKU ใด ๆ ต้องตรวจสอบกับผู้ใช้หน้างานอีกครั้งก่อน IMPLEMENTATION
